# Foresights v0.2 architecture — TypeScript-first dashboard template

> **Status:** Phase 1 design-of-record. Written 2026-05-19, partway through the v0.1 → v0.2 transition.
> Read this before opening any `.ts` file under `templates/`, before touching `biome.json` / `tsconfig.json` / `package.json`, and before changing the wizard's build pipeline.

## Why this exists

v0.1 left the Foresights dashboard as a single-file `templates/dashboard.html` with ~2,200 lines of inline JavaScript inside one `<script>` block. That's the shape the proven `aws-cdk-news` and `aws-serverless-news` dashboards ship in — Cowork artifacts ship as one HTML file and the runtime evaluates inline scripts as-is.

v0.2 keeps the shipped artifact a single HTML file (the runtime hasn't changed) but moves the **source of truth** to a modular TypeScript codebase under `templates/`. The wizard compiles, type-checks, lints, and bundles at build time, then injects the resulting JS into the HTML shell before calling `mcp__cowork__create_artifact`.

The reasons for the move (in order of weight):

1. **Type safety on a sharp surface.** The wizard generates code that the runtime evaluates. A typo in a generated `match` function or a missing field on a `Spotlight` object dies silently at runtime ("spotlight stuck on Loading…"). `tsc --strict` catches these before `create_artifact` ever runs.
2. **Testability.** ~2,200 LOC of behavior with no tests is a liability. Splitting into ~25 small modules with explicit `Deps` injection lets every unit be tested in isolation with mocked `callTool` / `askClaude` / `localStorage` / `Date.now`.
3. **Maintainability.** Future generator authoring (v0.3) writes against typed interfaces (`Source`, `Product`, `Spotlight`, `Brief`, `FlagMeta`) rather than guessing the JS object shape from the proven template.
4. **The wizard's own correctness.** A wizard that emits broken JS is a worse failure mode than a wizard that emits a clear "type error in PRODUCTS_CONFIG generator output". `tsc --noEmit` is the wizard's pre-flight check.

## What stays HTML / CSS vs what moves to TS

| Region | Format | Sentinels live in | Why |
|---|---|---|---|
| Markup (sections, nav, hero, footer, brief-all bar, digest bar, context bars) | HTML | `templates/dashboard.html` | HTML doesn't compile; the wizard's sentinel substitution stays plain string-replace. |
| Styling (per-product CSS overrides) | CSS in `<style>` | `templates/dashboard.html` | Same — CSS doesn't compile. PRODUCT_CSS sentinel stays HTML-side. |
| Behaviour (rendering, matchers, prompts, briefs, digests, boot) | TypeScript | `templates/*.ts` | All logic moves. The HTML's one `<script>` block becomes `<script>{{COMPILED_JS}}</script>`. |

## Tooling — biome + tsc + esbuild + Vitest

Four tools, each with a single responsibility.

**[biome](https://biomejs.dev)** — formatter + linter. One tool replaces ESLint + Prettier. Runs in CI (`npx biome check templates/`) and as the wizard's first build-pipeline step. Fast (Rust). Config in `templates/biome.json`.

**[tsc](https://www.typescriptlang.org/)** — type checker only. Invoked as `npx tsc --noEmit --project templates/tsconfig.json`. We do not use tsc for emit — that's esbuild's job. The wizard runs `tsc --noEmit` before bundling and aborts if it fails. Config in `templates/tsconfig.json` (strict, ES2022, moduleResolution bundler).

**[esbuild](https://esbuild.github.io)** — the bundler/emitter. Invoked as `npx esbuild templates/dashboard.ts --bundle --format=iife --target=es2022 --minify=false --sourcemap=inline`. Output: one JS bundle, IIFE-wrapped (so it can be inlined inside the HTML's `<script>` block without polluting global scope), source-mapped (for clickable stack traces inside the artifact). ~10ms cold.

**[Vitest](https://vitest.dev)** — unit + integration tests. Co-located `.test.ts` next to each module. Integration test uses JSDOM to load the compiled bundle into a fake DOM and asserts the boot block runs end-to-end with stubbed `Deps`. Config in `templates/vitest.config.ts`.

The four tools are devDependencies in `templates/package.json`. The wizard runs them via `npx` so the user's Cowork sandbox doesn't need them pre-installed.

## The Deps interface — dependency injection seam

Every module that needs runtime services (MCP calls, Haiku inference, storage, time, DOM access) takes a `Deps` parameter. This is the single seam that makes the codebase testable.

```ts
// types.ts
export interface Deps {
  callTool: (name: string, args: unknown) => Promise<unknown>;
  askClaude: (prompt: string, data: unknown[]) => Promise<string>;
  runScheduledTask: (taskId: string) => Promise<void>;
  storage: Storage;          // localStorage in browser, in-memory wrapper in tests
  now: () => Date;           // injectable so day-rotation logic is deterministic in tests
  document: Document;        // injectable so JSDOM works in node
  window: Window;            // for window.cowork access; tests inject a fake
}
```

In the browser, `dashboard.ts` constructs the real `Deps` at boot:

```ts
// dashboard.ts (entry)
const deps: Deps = {
  callTool: (name, args) => window.cowork.callMcpTool(name, args),
  askClaude: (prompt, data) => window.cowork.askClaude(prompt, data),
  runScheduledTask: (id) => window.cowork.runScheduledTask(id),
  storage: window.localStorage,
  now: () => new Date(),
  document: window.document,
  window: window,
};
boot(deps);
```

In tests, the same `boot(deps)` runs against a JSDOM `window` + an in-memory storage + frozen `now()`.

**Modules never reach for globals.** No bare `window.localStorage`, no bare `new Date()`, no bare `document.getElementById`. Everything goes through `deps`. The single exception: pure utilities (e.g. `escHtml`) that have no runtime dependencies.

## Sentinel placement in TS land

The 12 sentinels from v0.1 map to the new tree as follows. The wizard's substitution layer needs to know each sentinel's home file.

| Sentinel | File | Notes |
|---|---|---|
| RESOURCES_MARKUP | `dashboard.html` | HTML — unchanged. |
| TIPS_MARKUP | `dashboard.html` | HTML — unchanged. |
| PATTERNS_MARKUP | `dashboard.html` | HTML — unchanged. Generator must NOT emit `<span class="insights-tag">` (runtime injects via `upgradeHighlightBadges`). |
| HIGHLIGHTS_MARKUP | `dashboard.html` | HTML — unchanged. Same rule as PATTERNS_MARKUP. |
| SECTION_NAV | `dashboard.html` | HTML — unchanged. |
| SECTION_MARKUP:ABOVE_HIGHLIGHTS | `dashboard.html` | HTML — unchanged. First section block. |
| SECTION_MARKUP:BELOW_HIGHLIGHTS | `dashboard.html` | HTML — unchanged. Subsequent section blocks. |
| PRODUCT_CSS | `dashboard.html` | CSS in `<style>` — unchanged. |
| PRODUCT_UI_BARS | `dashboard.html` | HTML — brief-all bar, digest bar, context bars. |
| SOURCES_CONST | `templates/sources.ts` | `// FORESIGHTS_START:SOURCES_CONST` comment, wraps `export const SOURCES: Source[] = [...]`. |
| SPOTLIGHTS_CONST | `templates/spotlight/data.ts` | `// FORESIGHTS_START:SPOTLIGHTS_CONST`, wraps `export const SPOTLIGHTS: Spotlight[] = [...]`. |
| LOAD_BODY | `templates/boot.ts` | `// FORESIGHTS_START:LOAD_BODY`, wraps the body of `export const boot = async (deps: Deps): Promise<void> => {...}`. |
| PRODUCTS_CONFIG:PRODUCTS_CONST | `templates/products/config.ts` | Per-product label, badge colour, css mod. |
| PRODUCTS_CONFIG:RULES | `templates/products/rules.ts` | Per-product `Rule[]` arrays. |
| PRODUCTS_CONFIG:PROMPTS | `templates/products/prompts.ts` | Per-product system prompts. |
| PRODUCTS_CONFIG:CC_BUILDERS | `templates/products/cc-prompts.ts` | Per-product `buildCcPrompt` arrow fns. |
| PRODUCTS_CONFIG:CONTEXT_REFRESH | `templates/products/context-refresh.ts` | Per-product optional fetch/render/invalidate. |

15 distinct sentinel ranges across 12 logical generators. The wizard's substitution layer is per-file string replace; the multi-file nature only matters to the generators (e.g. the PRODUCTS_CONFIG generator outputs five strings, one per sub-sentinel home file).

## The wizard's new build pipeline

Step-by-step. Aborts on any failure with a clear error.

```
1.  Read templates/ tree (.html + all .ts + tsconfig.json + biome.json + package.json).
2.  Apply HTML sentinel substitutions to dashboard.html in memory.
3.  Apply TS sentinel substitutions across the .ts files in memory.
4.  Write the substituted tree to a temp working directory (e.g. /tmp/foresights-build-<uuid>/).
5.  Run `npx --yes @biomejs/biome check <tempdir>` — abort with biome errors if any.
6.  Run `npx --yes typescript@latest tsc --noEmit --project <tempdir>/tsconfig.json` — abort on type errors.
7.  Run `npx --yes esbuild <tempdir>/dashboard.ts --bundle --format=iife --target=es2022 --minify=false --sourcemap=inline` — capture stdout as the JS bundle.
8.  Substitute {{COMPILED_JS}} in <tempdir>/dashboard.html with the bundle.
9.  Run the integration smoke test: `npx --yes vitest run <tempdir>/tests/integration.test.ts` — abort on test failures.
10. Read the final dashboard.html and pass to mcp__cowork__create_artifact.
```

Steps 5, 6, 7, 9 all run through `mcp__workspace__bash` so they execute in the Linux sandbox. Sandbox has Node and npm preinstalled (verified). First-run latency: ~30s while `npx` downloads tools to a cache; subsequent runs ~5s.

## Testing approach

Two tiers.

**Unit tests** — co-located `<module>.test.ts` next to each `<module>.ts`. Each module has its dependencies passed in via `Deps`, so the test constructs a minimal `Deps` with stubbed `callTool` / `askClaude` and asserts the module's output. Aim for >80% line coverage in `util/`, `mcp/`, `products/matcher.ts`, `products/brief.ts`, `digest/triage.ts`, `digest/markdown.ts`.

**Integration test** — `templates/tests/integration.test.ts`. Spins up JSDOM, loads the compiled JS bundle, asserts `boot(deps)` completes without TDZ errors and that the expected DOM elements are populated. This is the spiritual successor to the v0.1 brief's "smoke-test the boot block before update_artifact" rule.

The wizard runs only the integration test as a pre-flight (step 9 of the build pipeline). Unit tests run in CI on every push.

## What's NOT in v0.2

These are explicit non-goals for the architecture as of this ADR. They're deferred to later iterations.

- **Per-block generator specs.** Only RESOURCES_MARKUP has a written generator spec as of this writing (in SKILL.md). The other 11 land in v0.3 once the architecture is stable.
- **Source maps that point back to the user's `templates/*.ts`.** The artifact ships with inline source maps (esbuild emits them), but they map to the post-substitution temp-dir paths, not the plugin's `templates/` tree. Stack traces inside the artifact will reference the bundle. Acceptable for v0.2.
- **Code splitting / lazy-loaded modules.** The bundle is one IIFE. ~2,200 LOC of JS is small enough to inline; we don't need on-demand loading.
- **Watch mode / hot reload while developing the template.** Devs run `npx vitest --watch` to get fast feedback on tests, but the dashboard.html → artifact loop still requires re-running the wizard.

## Open questions for v0.2.x

These will get decided as the relevant phase lands.

1. **How does the wizard handle a user-edited `templates/*.ts` after install?** Right now the wizard reads `templates/` from the plugin install dir, which is read-only. If the user customises their wizard's output, they'd need to edit the produced artifact post-hoc. v0.2.x or v0.3 might let `~/.claude/foresights/templates/*` shadow the plugin defaults.
2. **Source-map fidelity to plugin source paths.** Mentioned above as a non-goal but worth revisiting if stack-trace debugging becomes painful.
3. **Bundle size budget.** No budget yet. The proven aws-cdk-news is ~110 KB of inlined HTML+JS+CSS. Post-TS+sourcemap the budget will probably push 180 KB. If that becomes a Cowork-artifact-load-time issue, drop the source maps for a 40% size cut.
